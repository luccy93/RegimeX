# RegimeX Architecture Principles

**RegimeX — Open-Source Market Intelligence Platform**  
**Volume:** V03 — System Architecture  
**Status:** Approved Architecture Blueprint  

---

## 1. Purpose

This document establishes the fundamental engineering and architectural principles that govern the design, implementation, evolution, and maintenance of RegimeX. Every design decision, module boundary, public interface, and technical contribution must align with these principles.

These principles translate the core product values defined in `V01/PRINCIPLES.md` and the functional/non-functional requirements defined in `V02/SRS.md` into concrete technical guardrails.

---

## 2. Core Architectural Principles

### 2.1 Separation of Concerns

Each module, service, and architectural layer must have a single, clearly bounded responsibility.

- **Presentation** handles user interaction, layout, and visualization only. It contains no financial calculations or business rules.
- **Application / API** handles authentication, authorization, request validation, rate limiting, and workflow orchestration. It delegates domain computation to domain modules.
- **Domain Layer** encapsulates core financial logic (regime detection, risk estimation, feature math, backtesting). It is completely decoupled from transport protocols (HTTP, WebSockets), database technologies, and cloud providers.
- **Data Ingestion** isolates external market-data integration from internal consumption.

### 2.2 Dependency Inversion & Clean Boundaries

High-level domain modules must not depend on low-level infrastructure, specific database drivers, external API clients, or UI frameworks.

- Domain modules depend solely on abstractions (interfaces / protocols).
- Infrastructure adapters (SQL repositories, caching layers, external HTTP clients) implement these abstractions and are injected at runtime.
- Core business logic must be executable in isolation without starting a web server or database instance.

### 2.3 Provider Abstraction

The platform must never be coupled to a specific external market data vendor, news provider, or AI foundation model.

- All external integrations sit behind vendor-neutral abstraction layers (`MarketDataProvider`, `AIProviderAdapter`).
- Provider-specific payloads must be translated immediately into RegimeX canonical data structures at the boundary.
- Swapping or adding a data provider must require only writing a new adapter, with zero alterations to downstream feature engineering, regime detection, or backtesting logic.

### 2.4 Model Abstraction & Pluggability

Regime detection algorithms must be interchangeable, comparable, and independently extensible.

- Every regime detector (HMM, GMM, KMeans, Changepoint, ensemble, or custom community model) must conform to a unified conceptual contract.
- Downstream systems (regime intelligence, risk analytics, strategy backtesters) interact strictly with the abstract contract, never algorithm-specific internals.
- New quantitative algorithms can be introduced by community contributors without modifying existing analytics pipelines.

### 2.5 Immutable Research Inputs & Point-in-Time Correctness

Financial research is meaningless without temporal integrity.

- **Strict No-Look-Ahead Bias:** Computation at timestamp $T$ must strictly consume information available at or before timestamp $T$. Any leak of future information is classified as a critical defect (P0).
- **Immutable Input Snapshots:** Analytical runs, backtests, and regime classifications must bind to immutable, version-fingerprinted datasets. Once ingested, historical tick/bar data is append-only and immutable for a given adjustment version.

### 2.6 Reproducibility by Design

Every analytical result generated by RegimeX must be bit-for-bit reproducible across time, environments, and machines.

- Any regime timeline, risk metric, or backtest run must be uniquely identifiable and reconstructible from its recorded lineage:
  $$\text{Result} = f(\text{Dataset Version}, \text{Feature Set Version}, \text{Model Version}, \text{Parameters}, \text{Seed})$$
- Deterministic algorithms must yield identical outputs given identical inputs. Stochastic algorithms must accept and record explicit random seeds.
- All software versions, environment parameters, and computation metadata must be captured in provenance audit logs.

### 2.7 Explicit Uncertainty Communication

Financial markets are inherently non-stationary and stochastic. RegimeX strictly rejects false precision.

- Regime detection models must provide probability distributions, transition likelihoods, or confidence scores alongside discrete regime labels wherever mathematically supported.
- Risk analytics must state confidence levels, historical sample windows, and underlying distribution assumptions.
- The platform UI, API responses, and AI assistant outputs must visibly communicate uncertainty rather than displaying definitive assertions.

### 2.8 Secure-by-Default Design

Security is an architectural foundation, not an operational afterthought.

- **Zero Trust Boundaries:** All external inputs (HTTP parameters, JSON payloads, file uploads) must be strictly validated against typed schemas at the edge before passing to domain services.
- **Least Privilege:** API keys, database roles, and service workers operate with the minimum necessary read/write scopes.
- **No Plaintext Secrets:** Credentials, API tokens, and private keys must never exist in source code, committed files, logs, or unencrypted storage.
- **Fail Securely:** When authorization, validation, or dependency checks fail, the system must fail closed, emitting structured security audit events.

### 2.9 Observable-by-Default Design

Every component of RegimeX must be observable without inspecting raw code or attaching debuggers to production instances.

- **Structured Telemetry:** All subsystems emit machine-readable JSON logs with correlated trace IDs (`request_id`, `job_id`, `run_id`).
- **Telemetry Pillars:** Comprehensive coverage across structured logging, Prometheus-compatible metrics, distributed tracing, and health endpoints (`/health` liveness, `/ready` readiness).
- **Incident Queryability:** Operators must be able to resolve: *What failed? When? In which component? With which dataset/model? Can it safely retry?*

### 2.10 Asynchronous & Non-Blocking Workloads

Interactive user journeys must never be degraded by heavy quantitative workloads.

- High-latency, computationally intensive tasks (multi-year ingestion, feature matrix calculation, ML model fitting, Monte Carlo simulation, walk-forward backtests) must be decoupled into asynchronous background jobs.
- Interactive API endpoints and web dashboards must remain responsive, returning immediate job identifiers and status polling endpoints.

### 2.11 Graceful Degradation & Resilience

Partial failures must not cause catastrophic platform collapse.

- If an external market data provider goes offline, cached data, historical analytics, and independent backtests must continue functioning.
- If an external AI provider experiences an outage, core quantitative dashboards and calculations must operate uninterrupted, returning an informative fallback message for AI-assisted queries.
- Dependencies must implement retry policies with exponential backoff and jitter, circuit breaking, and dead-letter queues.

### 2.12 Backwards-Compatible Interfaces

The platform must respect consumer stability across its evolutionary lifecycle.

- Public REST API contracts, SDK methods, and plugin interfaces follow semantic versioning.
- Non-breaking changes (additive fields, optional parameters) must not alter existing field semantics or break existing API consumers.
- Breaking changes require formal deprecation notices, version increments, and migration paths.

### 2.13 Open-Source Extensibility & Self-Hostability

RegimeX is built for the global quantitative research and development community.

- **Zero Vendor Lock-in:** The system must run completely on standard, open-source technology stacks (PostgreSQL/TimescaleDB, Redis, Python, Docker) without mandatory commercial cloud dependencies.
- **Local Developer Simplicity:** A contributor must be able to spin up the entire operational environment locally with standard container tooling (`docker compose up`) in under 15 minutes.
- **Clear Extension Points:** Well-documented plugin interfaces allow external researchers to add proprietary features, custom detectors, or private data sources without forking the core engine.
