# ADR-0005: Regime Detector Interface Design

**Status:** Accepted  
**Date:** 2026-09-03  
**Volume:** V03 — System Architecture  
**Deciders:** RegimeX Core Architecture Team  

---

## 1. Context

Market regime detection is a multifaceted quantitative problem with diverse mathematical formulations:
- **Hidden Markov Models (HMM):** Infer unobserved latent states through time-dependent transition probability matrices.
- **Gaussian Mixture Models (GMM):** Model asset returns and volatility features as probabilistic mixtures of Gaussian clusters without temporal transition dynamics.
- **K-Means / Geometric Clustering:** Deterministically partition feature spaces into discrete clusters.
- **Change Point Detection (e.g., PELT, BOCPD):** Detect structural break boundaries and shifts in mean/variance over time.
- **Ensemble & Community Deep Learning Models:** Combine multiple detector outputs or evaluate future neural sequence architectures.

Downstream systems—including the Regime Intelligence Engine (transition matrices, regime persistence), the Risk Engine (regime-conditional VaR, CVaR), the Backtesting Engine (regime-aware asset allocation and attribution), and the Web Presentation Tier—require consistent access to regime outputs.

If each algorithm exposed an idiosyncratic API, every downstream consumer would require complex conditional logic (`if algorithm == 'hmm' ... elif algorithm == 'gmm' ...`), creating an unmaintainable codebase that discourages algorithmic research and community contributions.

---

## 2. Decision

> **All regime detection algorithms must conform to a unified conceptual contract (`RegimeDetector`), allowing downstream analytical engines to remain completely model-agnostic.**

### Contract Specifications:
1. **Core Lifecycle Contract:**
   - `fit(feature_matrix)`: Trains algorithm parameters strictly on in-sample historical feature data. Returns `self`.
   - `predict(feature_matrix)`: Generates discrete integer regime state labels ($0, 1, \dots, K-1$) matching the input length.
   - `predict_proba(feature_matrix)`: Outputs continuous posterior probability vectors across all $K$ regimes (rows sum to $1.0 \pm 10^{-6}$). For non-probabilistic models (e.g., standard K-Means), calibrated distance-based confidence vectors or one-hot approximations must be returned.
   - `metadata()`: Exposes human-readable algorithm name, mathematical family, assumptions, known failure modes, and input requirements.
   - `get_params()`: Returns the complete hyperparameter dictionary for exact historical reproduction.
2. **Model Versioning:** Each detector implementation includes an immutable `algorithm_id` and semantic version (e.g., `hmm_gaussian_v1`). Modifying mathematical logic requires a version increment.
3. **Model-Agnostic Downstream Consumers:**
   - **Transition Matrix Calculator:** Operates strictly on the output sequence of discrete state labels or probability matrices, regardless of whether generated by HMM, GMM, or PELT.
   - **Risk Analytics:** Groups returns by detected state ID ($k \in \{0, \dots, K-1\}$) and computes state-conditional statistics.
   - **Backtesting Allocator:** Receives current regime state or probability distribution on each chronological bar and executes strategy logic without knowing model internals.
4. **Supported Algorithm Families:** The contract natively accommodates HMM, GMM, K-Means, Change Point Detection, and future community models.
5. **Compliance Test Harness:** All detectors must pass automated compliance tests in `tests/compliance/test_regime_detector_compliance.py` asserting shape correctness, numerical stability, and look-ahead bias absence.

*Note: Algorithm implementations begin in V08 (HMM) and V10 (GMM / Clustering).*

---

## 3. Alternatives Considered

| Alternative | Description | Why Rejected |
|-------------|-------------|--------------|
| **Standard scikit-learn BaseEstimator Only** | Relying strictly on `fit` and `predict` from scikit-learn. | Does not mandate standardized metadata, financial assumption disclosures, hyperparameter versioning, or probabilistic normalization checks. |
| **Separate Contracts per Algorithm Family** | Distinct interfaces for Markov models vs clustering vs changepoint detectors. | Forces downstream risk and backtesting engines to write custom branches for every family; breaks algorithmic interchangeability. |
| **Monolithic Detector Switch** | A single detector class containing internal branching logic for all algorithms. | Violates the Open/Closed Principle; prevents contributors from adding custom models cleanly without modifying core repository files. |

---

## 4. Consequences

### Positive
- **True Algorithmic Pluggability:** Researchers can implement and benchmark new models simply by adhering to `RegimeDetector`.
- **Decoupled Downstream Architecture:** Risk, attribution, and visualization engines interact with standardized state labels and probabilities without caring how they were inferred.
- **Enforced Scientific Rigor:** Standardized metadata and parameter serializability guarantee experimental reproducibility across all models.
- **Strict Uncertainty Disclosure:** Mandatory probability/confidence vectors enforce RegimeX's core principle of explicit uncertainty communication.

### Negative / Trade-offs
- **Adapter Overhead for Deterministic Models:** Algorithms that do not naturally produce probability distributions (such as K-Means or PELT) must implement synthetic or calibrated probability approximations for `predict_proba()`.
